## 1. Mission

Implement the first deterministic, evidence-backed GPIO verification capability for INVENTOR EDU.

The checker must evaluate explicitly requested GPIO functions against:

1. Validated physical terminal identity.
2. Verified board-terminal-to-SoC mapping.
3. Source-backed silicon GPIO capabilities.
4. Board-specific resource restrictions.
5. Available operating-state evidence.
6. Explicit evidence trust and version boundaries.

Use the existing CORE-001A-R2 engineering model.

**Do not create a new canonical engineering model, graph engine, simulator, inference engine or general-purpose rules framework.**

The core requirement is:

> Given an exact device profile, a validated circuit snapshot, an explicitly selected physical terminal, a requested GPIO capability, and a trusted evidence set, return a deterministic, correctly scoped engineering finding.

The system must distinguish an unsupported function from a missing fact, an unavailable board resource from a physically incapable silicon pin, and a supported GPIO capability from actual firmware activity or electrical compatibility.

### Expected product result

A learner selecting the ESP32 board's GPIO34 contact and requesting output functionality must receive a defensible negative finding.

A learner selecting a sourced GPIO18 contact and requesting ordinary GPIO output must receive a positive **physical-capability finding only** when every required evidence gate is satisfied.

Neither result establishes whether connected hardware is electrically safe or whether a running firmware program has configured that GPIO.

## 2. Approved architectural choices

The architecture owner freezes the following choices for this task.

### Computation

Use typed finite-domain predicates, comparisons, membership checks and explicit conjunctions.

Use deterministic Python functions and the existing Pydantic runtime.

Do not introduce:

- Z3 or another SMT/SAT solver.
- KiCad ERC as a runtime dependency.
- ngspice or another circuit simulator.
- ESP-IDF as an embedded backend runtime.
- Zephyr as a runtime dependency.
- A new canonical graph.
- A generic rule expression language.
- LLM-based runtime verification.

No new third-party package is authorized.

### Engineering separation

Preserve:

- `CORE-001A`: physical terminals, validated snapshots and topology.
- `CORE-001B`: GPIO functions, board availability and explicitly supported configuration conditions.
- `CORE-001C`: electrical voltages, currents, impedance, loading and physical compatibility.
- Future firmware tools: independently observed runtime state.

These are different verification responsibilities.

### Device independence

The evaluation functions must not contain conditional logic such as:

`if board == "ESP32" and gpio == 34`

or otherwise embed named silicon GPIO numbers as business rules.

Device-specific facts belong in independently versioned fact profiles.

The same generic capability rules must support a synthetic non-ESP32 device without changing the evaluator.

## 6. First supported verification scope

Implement only the following requested operations.

### Supported functional requests

- `GPIO_IN`
- `GPIO_OUT`
- `GPIO_IN_PULLUP`

The third request represents GPIO input with an explicitly requested internal software pull-up. It does not imply that an external circuit has suitable biasing or voltage levels.

### Supported checks

**A. PIN_MAPPING**

Determine whether the requested physical terminal has independently verified, uniquely scoped `soc_gpio` mapping evidence.

**B. PHYSICAL_CAPABILITY**

Determine whether the selected silicon GPIO supports the explicitly requested input/output function.

**C. BOARD_AVAILABILITY**

Determine whether the exact board profile reserves the mapped resource for flash or another explicitly documented non-releasable purpose.

**D. INTERNAL_PULLUP_CAPABILITY**

Determine whether the selected GPIO supports the requested internal software pull-up.

**E. BOOT_STRAP_CONTEXT**

For a documented strapping GPIO, represent the boot-related condition separately.

Absent reset-time level, external pull and sampling evidence must not be interpreted as boot failure.

**F. ACTIVE_CONFIGURATION**

Preserve the distinction between possible functionality and observed firmware configuration.

A missing runtime observation cannot produce active-configuration PASS.

Actual firmware instrumentation is outside this task.

### Unsupported functions

The initial implementation must not pretend to support:

- PWM output assignment.
- ADC selection and conversion.
- UART pinmux validation.
- I2C peripheral ownership.
- SPI resource planning beyond explicitly sourced board reservations.
- Multi-peripheral arbitration.
- Firmware emulation.
- Live pin-state acquisition.
- Electrical voltage compatibility.
- Analog noise simulation.

Requests outside the supported scope must be explicitly recorded as not evaluated.

Do not invent capability data merely to implement a wider Research B rule.

## 9. Result semantics — explicitly approved reconciliation

The existing repository verification policy remains authoritative for engineering finding statuses.

Use:

- `PASS`
- `FAIL`
- `UNKNOWN`
- `NOT_APPLICABLE`

Research B's `INDETERMINATE` corresponds to `UNKNOWN` when a supported, applicable check lacks sufficient evidence.

Do not collapse unsupported functionality into `NOT_APPLICABLE`.

Introduce a distinct coverage field:

- `EVALUATED`
- `NOT_EVALUATED`

A supported check with missing evidence should have an evaluated `UNKNOWN` finding.

A request for an unsupported verifier operation should produce a coverage record with `NOT_EVALUATED` and an explicit reason.

`NOT_APPLICABLE` is reserved for a supported rule demonstrated not to apply to the given request or conditions.

Do not emit an artificial `PASS` merely to fill a result field.

Every finding must contain at least:

- requirement ID
- rule ID and version
- engineering status
- reason code
- severity
- physical terminal reference
- affected net, when relevant
- requested function
- relevant hardware scope
- evidence claim references
- missing prerequisites where applicable
- catalog digest
- snapshot digest
- fact-set digest
- rule-set version

Separate `severity` from status.

Use stable reason codes rather than locale-dependent explanatory prose.

## 10. Approved initial capability facts

Use the following facts as the bounded source-review targets.

These are not permission to publish an unrestricted hardware catalog.

### ESP32 GPIO34

- Input capability: supported.
- Output capability: unsupported.
- Internal software pull-up: unsupported.

Expected checks:

- `GPIO_OUT` → `FAIL / OUTPUT_NOT_CAPABLE`
- `GPIO_IN` → `PASS / CAPABILITY_CONFIRMED`
- `GPIO_IN_PULLUP` → pull-up check `FAIL / PULLUP_NOT_CAPABLE`

### ESP32 GPIO18

- Ordinary digital GPIO output is supported.

Expected:

- `GPIO_OUT` physical capability → `PASS / CAPABILITY_CONFIRMED`
- Active firmware configuration absent → `UNKNOWN / ACTIVE_CONFIG_UNKNOWN`

### ESP32 GPIO19

- Ordinary digital GPIO input is supported.

Expected:

- `GPIO_IN` physical capability → `PASS / CAPABILITY_CONFIRMED`

This does not assert that connecting HC-SR04 Echo at 5 V is safe.

### ESP32 GPIO6 / flash reservation

Research B identifies flash resource reservations on the selected board profile.

A source-backed board-resource fixture must distinguish:

- Silicon output capability.
- Board-level resource availability.

For a verified board contact mapped to a flash-reserved resource:

`FAIL / RESERVED_RESOURCE` applies to the relevant general-purpose board-use request.

Do not replace this rule with `OUTPUT_NOT_CAPABLE` unless a separate silicon capability fact independently establishes that result.

### Boot-strapping

The research identifies GPIO0, GPIO2, GPIO5, GPIO12 and GPIO15 as strapping-related GPIOs.

Use these as source-review candidates.

Do not generate a positive or negative boot-operation conclusion without the relevant board, reset, timing and level conditions.

If the selected physical board terminal cannot be independently tied to a strapping GPIO, do not fabricate a header mapping.

### Hardware identity

First fixture:

- ESP32-DevKitC V4
- ESP32-DevKitC-32E
- ESP32-WROOM-32E
- Exact reviewed board-header contact

Silicon facts must not be silently applied to a different chip or board revision.
