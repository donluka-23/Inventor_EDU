## 1. Mission

Implement the first real, deterministic circuit-connection candidate generator for INVENTOR EDU.

The generator must:

1. Accept a typed set of engineering signal roles.
2. Accept reviewed finite domains of physical terminals.
3. Enumerate eligible assignments without device-name-specific algorithm branches.
4. Construct real `Conductor` records.

6. Calculate actual net membership through `compute_nets`.
7. Invoke the existing CORE-001B GPIO verifier.
8. Preserve failed, unresolved and not-evaluated constraints.
9. Produce alternative candidates and reproducible decision traces.
10. Expose the computed information needed for future Georgian educational hints.

This task is not a frontend, natural-language parser, full component matcher or electrical simulator.

## 6. Generator operation

Implement a deterministic finite-domain generator.

### Step 1 — Input validation

Validate:

- exact catalog reference;
- component definition digests;
- physical terminal existence;
- supported role/function vocabulary;
- evidence and trust scope;
- domain bounds;
- uniqueness constraints;
- resource limits.

### Step 2 — Candidate enumeration

Enumerate role-to-terminal assignments using stable ordering.

For this small fixture, ordinary bounded backtracking is sufficient.

Use a declared `AllDifferent` constraint for the two roles.

Do not apply this uniqueness assumption universally to future shared-bus interfaces.

### Step 3 — Canonical construction

For each candidate:

- create exact `TerminalRef` endpoints;
- create deterministic `Conductor` IDs;
- build a `CircuitSnapshot` through `create_snapshot`;
- calculate topology through `compute_nets`;
- retain the canonical snapshot digest;
- record exact role→terminal→net relationships.

Do not infer physical connectivity from a future UI.

### Step 4 — GPIO verification

Generate `GpioRequirement` records with appropriate function and operating state.

Request the complete scope of checks required for this scenario:

- `PIN_MAPPING`
- `PHYSICAL_CAPABILITY`
- `BOARD_AVAILABILITY`
- `ACTIVE_CONFIGURATION`
- `ELECTRICAL_COMPATIBILITY`

Invoke `verify_gpio_requirements()` directly.

Do not use `analyze_hcsr04_wiring()` as a generic generator; its existing exact-profile behavior must remain unchanged.

### Step 5 — Classification

Keep actual CORE-001B findings and coverage unchanged.

Classify candidates separately as:

- `REJECTED_KNOWN_HARD_FAIL`
- `SCOPED_CHECKS_PASSED_WITH_OBLIGATIONS`
- `INCOMPLETE_WITH_EXPLICIT_OBLIGATIONS`

At search level distinguish:

- `EXHAUSTED_REVIEWED_DOMAIN`
- `SEARCH_INCOMPLETE`
- `NO_REVIEWED_DOMAIN`

These classifications must never be exposed as `SAFE`, `FULLY_COMPATIBLE` or `READY_TO_BUILD`.

If GPIO direction passes but board availability is UNKNOWN, the candidate remains incomplete.

If an electrical rule is NOT_EVALUATED, it remains a proof obligation.

## 7. Evidence and explanation trace

For each candidate record:

- originating requirement ID;
- assignment ID;
- exact component instance;
- exact physical terminal;
- computed net ID;
- raw `GpioFinding` references;
- separate `GpioCoverage` references;
- reason codes;
- source/evidence claim IDs;
- catalog, snapshot and fact-set digests;
- source/operating-condition restrictions;
- unresolved obligations;
- generator and pattern versions.

`GpioCoverage` must remain distinct from `GpioFinding` even though they share common result fields.

A missing finding must never be replaced with a fabricated finding ID.

This trace will become the input for future Georgian educational hints.

No natural-language explanation generator is authorized in SYN-001.

## 8. Alternative generation

The generator must demonstrate a real search procedure.

Required behavior:

- GPIO34 chosen for Trig produces a physical capability FAIL.
- The rejected assignment is preserved with its actual reason.
- Another available candidate, such as GPIO18, is evaluated using a new canonical snapshot.
- The subsequent direction capability may PASS within its actual scope.
- The new result must not inherit the old snapshot's findings.
- The electrical and firmware obligations remain unresolved.

The engine must not simply return a stored mapping of:

`Trig → GPIO18`

or:

`Echo → GPIO19`.

It must discover assignments through the provided domains, construct them and actually run the verifier.

---

## 9. Bounded search

Implement a deterministic search-node budget.

If the budget ends before the reviewed finite domains are exhausted:

- return `SEARCH_INCOMPLETE`;
- report visited and rejected counts;
- preserve candidates already evaluated;
- never claim the domain is exhausted;
- never claim no valid physical circuit exists.

`max_candidates` limits returned results, not proof of complete search.

Use stable ordering and deterministic tie-breaking.

Record actual candidate counts, verifier calls and runtime measurements.
